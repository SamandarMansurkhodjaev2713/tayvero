# Team tasks UI review — 2026-10-06

This review covers the application UI, not PostgreSQL acceptance or browser verification. The interface uses the existing TAYVERO Operate identity, semantic tokens, shared controls and client boundary. No backend permissions are implemented in UI code; controls reflect the API's current permission fields and every write still reaches the protected server procedure.

## Delivered flow

- Dashboard Mine/Team tasks share the existing overview scope, with visible copy explaining that changing this selection also changes the overview. Changing scope remounts the queue, resetting page, selected task and mutation feedback. The old creator-only overdue card is removed; analytics remain.
- `activities.taskQueue` supplies actual assignment, 25-row pages, total matches and scoped status counts. Team also offers All responsible people, Unassigned or a searchable active member filter; changing it resets the page/editor and counts explicitly reflect that same responsibility filter. Mine hides and omits this filter. Open/completed/all views expose every returned row, including undated, future and invalid-date tasks. Completed tasks offer Reopen. Mine means assigned to the viewer; creator is shown separately.
- Existing record timelines offer Edit/history or read-only History. `taskById` loads current details independently of the filtered queue; `updateTask` and completion send `expectedVersion`. Queue, detail and history caches invalidate together after confirmed writes.
- The CRM composer creates assigned, self-defaulted or explicitly unassigned TASK activities. Native datetime-local exposes exact date and time. A blank means no deadline; no calendar-only midnight or hidden hour is invented. Non-task activities do not receive task assignment/deadline fields.
- History renders recorded assignee name snapshots, actor, version and before/after responsibility/deadline. Legacy missing names have an understandable fallback; missing creation history is acknowledged. Only the latest 50 events are requested, and the limit is visible.

## Critical iterations and concrete corrections

| Lens | Defect or risk challenged | Result |
| --- | --- | --- |
| Responsibility and authorization | “My tasks” previously meant immutable author, not responsible person; missing picker results could falsely suggest revoked membership. | Queue uses real assignee semantics and creator provenance. `canEdit`/`canReassign` control actions separately. Revocation copy uses the API's actual `assigneeActive` signal; search absence preserves the selected name without making membership claims. |
| Temporal integrity | A date-only creation control silently scheduled local midnight; native Date rollover can accept impossible dates and DST gaps. | Creation and editing share a roundtrip-validated local datetime parser. It rejects rolled dates and nonexistent DST hours, serializes an ISO instant and explains device timezone/repeated-hour behavior. An unchanged edit preserves the exact existing instant, including seconds and either repeated-hour occurrence. Omitted edits preserve values; explicit blanks/null clear them. |
| Concurrency and recovery | Background version refresh could wipe the user's unsaved form; stale writes could overwrite another member's change. | Editor pins the draft's original version without remounting on refresh. A newer version blocks saving, retains the draft and labels explicit reload as discarding unsaved values. Mutation errors preserve draft; failed refresh blocks changes until recovery. Completion/reopening also send the displayed version. |
| Count and navigation truth | Client slices and capped queries could imply complete task totals; completion grouping could hide reopened tasks; finding unassigned work could require paging through unrelated people. | Server pagination and total match count replace a snapshot claim. Calendar bucket counts explicitly say “on this page”; all 25 returned rows remain reachable. The Team responsibility filter queries unassigned or a specific active member directly and applies to the server counts too. Completed rows have their own visible group. A later page emptied by concurrent changes offers first-page recovery rather than claiming no tasks. |
| Accessibility and constrained layout | Long names, subjects, task rows and editor controls could overflow or lack keyboard access. | Existing wrap-anywhere classes, flex wrapping, min-width safeguards and bounded dialog/list scrolling preserve compact layouts. The single independently scrolling labelled section is keyboard-focusable with a narrowly explained Biome exception. Shared labelled controls, native future-task disclosure, status/alert feedback and visible pending/disabled actions are retained. This is source/SSR evidence, not measured browser layout evidence. |
| Traceability and readability | History displayed unfamiliar member IDs and current names could misrepresent earlier responsibility after rename/departure. | Recorded name snapshots take precedence. Current known names are a legacy fallback; unknown people display “Former or unavailable member”. Actor/version and before/after dates remain visible. No notification or provider-delivery claims are introduced. |
| Mutation and cache consistency | Competing completion/view changes and orphaned caches could show a success before the refreshed task was known. | Pending actions disable competing queue controls and editor closure. Success feedback follows acknowledged mutation and awaited activity invalidation. Creation/update/complete invalidate queue, detail, history, CRM records and dashboard using the existing cache helper. No optimistic completion is presented as confirmed success. |
